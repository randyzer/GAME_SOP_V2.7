# V2.6_CHANGE_PROPOSAL — V0.2

## Status

- Purpose: Consolidated production-hardening proposal for `GAME_SOP`, `GAME_CODEX_MASTER_PROMPT`, and `GAME_SITE_STARTER`
- Evidence base: Bomb Farm + Afterworld real-world production use
- Relationship to V2.5: hardening release, not architecture rewrite
- Current state: proposal only; frozen V2.5 remains unchanged

# 0. Decision Summary

V2.6 should not implement six isolated fixes.

The six observed issues should be consolidated into four cohesive change packages:

```text
Package A — Evidence Resilience
Package B — C2C Review Reliability
Package C — Visual & Media Governance
Package D — Starter Media Contract Fixes
```

This structure is preferred because it:

- reduces duplicated rules;
- keeps methodology concerns out of the Starter;
- keeps technical contract fixes out of the SOP;
- preserves High Cohesion / Low Coupling;
- avoids turning V2.6 into a new architecture generation.

The implementation order should be:

```text
1. Freeze this V0.2 proposal
2. Update GAME_SOP V2.6 candidate
3. Update GAME_CODEX_MASTER_PROMPT V2.6 candidate
4. Update GAME_SITE_STARTER only for proven technical defects
5. Run Bomb Farm regression
6. Run Afterworld regression
7. Run one third-game real-world test
8. Fix only newly proven blockers
9. Freeze V2.6
```

# 2. Evidence Base

## 2.1 Bomb Farm

Bomb Farm exposed the first major visual regression:

```text
technical implementation valid
+
site operational
+

```

This drove the V2.5 additions around:

- visual planning
- media decisions
- no-media Hero behavior
- Human Content / Visual Gate
- semantic theme tokens

## 2.2 Afterworld

Afterworld reproduced the same failure after the complete V2.5 workflow had already passed:

- Phase 0–4 passed
- C2C passed
- build passed
- tests passed
- reconciliation passed
- desktop/mobile technical visual checks passed

Yet Human review found:

1. the palette did not sufficiently reflect the real game's visual language;
2. the site had almost no images compared with the strongest competitor.

The dedicated visual/media recovery then:

- added official key art to the homepage;
- added semantically matched images to eight core guides;
- revised theme tokens toward the actual game palette;
- added an intentional YouTube fallback;
- materially improved game recognition and media parity.

This establishes a repeated regression class rather than a one-off implementation error.

# 3. Package A — Evidence Resilience

## 3.1 Problems Covered

This package consolidates:

- V2.6-01 — Provenance Transport Dependency
- V2.6-03 — Official Source Reader Transport Dependency

Observed examples:

- `gh api` transient EOF while `git ls-remote` could still verify the same frozen tag/ref chain.
- Jina Reader HTTP 401 while a Human-authorized read-only browser could still verify the official source.

## 3.2 Root Cause

V2.5 sometimes couples:

```text
evidence validity
```

too closely to:

```text
one preferred transport/tool
```

That is incorrect.

A transport failure does not imply evidence failure.

## 3.3 New Shared Principle

Add a single cross-phase rule:

```text
Verification must be evidence-based,
not transport-dependent.
```

Standard flow:

```text
Preferred read-only transport
→ classify transport/auth/session failure
→ approved read-only fallback
→ preserve original failure evidence
→ preserve source/provenance identity
→ verify equivalent evidence
→ continue if verification succeeds
```

Only BLOCK when:

```text
required evidence itself cannot be verified
```

not merely when:

```text
one tool fails
```

## 3.4 Failure Classification

Use a small, explicit vocabulary:

```text
READ
PARTIAL
UNAVAILABLE
TRANSPORT_BLOCKED
AUTH_BLOCKED
```

Where relevant, provenance verification may additionally record:

```text
PRIMARY_TRANSPORT_FAILED
FALLBACK_VERIFIED
```

Do not create a generalized workflow engine for these states.

## 3.5 Permitted Fallback Examples

Depending on the evidence type:

- `gh api` → `git ls-remote`
- preferred page reader → Human-authorized read-only authenticated browser
- one official page → official alternate/localized first-party representation

## 3.6 Forbidden Fallback Behavior

Do not:

- bypass anti-bot systems;
- solve CAPTCHA;
- export browser cookies;
- perform write actions;
- silently replace first-party evidence with lower-authority evidence;
- erase the failed primary transport from history.

## 3.7 Layer Ownership

### GAME_SOP

Strong ownership.

Add:

```text
Verification Transport Resilience Policy
```

Cover:

- failure classification;
- fallback conditions;
- evidence equivalence;
- blocker criteria;
- audit/history preservation.

### GAME_CODEX_MASTER_PROMPT

Strong ownership.

Require the execution agent to:

- try preferred channel;
- classify failure;
- use approved fallback;
- preserve both failure and success evidence;
- not label evidence invalid solely because a transport failed.

### GAME_SITE_STARTER

No change.

## 3.8 Acceptance Criteria

PASS when:

- `gh api` fails but frozen provenance is independently verified through an approved read-only fallback;
- a preferred official-page reader fails but the same official source is verified through an approved read-only fallback.

BLOCK only when evidence itself remains unverifiable.

# 4. Package B — C2C Review Reliability

## 4.1 Problems Covered

This package consolidates:

- V2.6-02 — C2C Reviewer Capability / Evidence Access

Observed failures:

- Phase 0 reviewer lacked access to upstream frozen tag/ref evidence and returned BLOCKED despite correct local execution.
- Phase 3 reviewer could not initially inspect execution/QA evidence; after evidence was exposed through the read-only review channel, it returned DONE.

## 4.2 Root Cause

V2.5 validates:

```text
review outcome
```

without first validating:

```text
reviewer capability
```

A reviewer can be asked to verify evidence it cannot access.

## 4.3 New Principle

Add:

```text
Reviewer Capability Preflight
```

before evidence-dependent C2C review.

Independence means:

```text
independent access to sufficient evidence
```

not:

```text
same tool
same transport
same execution environment
```

## 4.4 Preflight Questions

Before INIT / EXECUTED review, establish whether the reviewer can inspect the evidence classes required for the task:

- upstream Git refs / provenance;
- current project status;
- execution summaries;
- test/build evidence;
- route/reconciliation evidence;
- source evidence;
- visual evidence when applicable.

## 4.5 Result Classification

If required evidence is inaccessible because of reviewer capability:

```text
REVIEWER CAPABILITY BLOCKED
```

Do not label:

```text
PROJECT BLOCKED
```

unless the project evidence itself is defective.

If evidence can be exposed safely through an approved read-only channel:

- expose it;
- rerun review;
- preserve the earlier blocked attempt in history.

## 4.6 C2C Evidence Publication Rule

Before EXECUTED review:

- ensure concise execution evidence exists;
- ensure the reviewer-readable channel contains enough proof;
- do not rely on unsupported statements such as “tests passed” if the reviewer cannot inspect any evidence.

Do not send:

- credentials;
- tokens;
- cookies;
- raw secret-bearing logs.

## 4.7 Layer Ownership

### GAME_SOP

Strong ownership.

Define:

- capability preflight;
- reviewer independence;
- reviewer-limitation classification;
- history preservation.

### GAME_CODEX_MASTER_PROMPT

Strong ownership.

Before every evidence-dependent C2C review:

- identify required evidence;
- confirm accessible evidence channel;
- classify capability gaps before sending review.

### GAME_SITE_STARTER

No change.

## 4.8 Acceptance Criteria

The workflow must reliably distinguish:

```text
implementation defect
```

from:

```text
reviewer evidence-access limitation
```

and must not force a project failure merely because the reviewer is under-equipped.

# 5. Package C — Visual & Media Governance

## 5.1 Problems Covered

This package consolidates:

- V2.6-04 — Visual / Media False PASS
- V2.6-05 — Incomplete Media Lifecycle

These should be treated as two halves of one system:

```text
Visual Gate
= determine whether the final result is good enough

Media Lifecycle
= ensure approved visual/media plans actually reach implementation
```

## 5.2 Severity

Critical.

This is the highest-priority V2.6 package.

## 5.3 Repeated Failure Pattern

Bomb Farm and Afterworld both showed:

```text
build PASS
tests PASS
responsive PASS
reconciliation PASS
technical visual QA PASS

but

game recognition weak
media richness weak
final site materially behind strongest competitor
```

Therefore:

```text
Technical Visual QA
!=
Human Visual Quality
```

## 5.4 New Quality Requirement — Game Recognition Gate

Add a first-class:

```text
GAME RECOGNITION GATE
```

Human Visual approval must explicitly answer:

1. Does the site immediately look like this specific game?
2. Are real game visual cues materially represented?
3. Is the palette derived from the game itself rather than only the publisher website?
4. Are high-value pages visually supported?
5. Is useful media richness materially below the strongest competitor?
6. Are selected images semantically matched to page topics?
7. Is no-media an intentional exception instead of the easiest default?
8. Does third-party media failure still look intentional rather than broken?

## 5.5 Official Visual Evidence

Phase 1 must prioritize actual game evidence in this order:

1. official key art
2. Steam capsule
3. gameplay screenshots
4. in-game UI
5. world/map visuals
6. official trailers
7. Dev Diary imagery
8. concept art
9. publisher marketing-page UI only as secondary evidence

Explicit rule:

```text
Corporate Web Color
!=
Game Visual Identity
```

## 5.6 Required Planning Output

Keep this inside `PROJECT_BRIEF.md` or another existing planning authority where possible.

Do not create a new standalone visual document by default.

Required section:

```text
Official Visual Evidence
```

It should record:

- primary palette;
- secondary palette;
- environmental lighting;
- UI/material language;
- map/world language;
- image style;
- recurring texture/shape language;
- what not to use;
- `VERIFIED / OBSERVED / DERIVED` status.

## 5.7 Competitor Visual & Media Benchmark

`COMPETITOR_ANALYSIS.md` must include a representative media benchmark against the strongest competitor.

Compare:

- homepage hero;
- article hero usage;
- screenshots on representative guides;
- videos;
- map imagery;
- thumbnails;
- galleries where relevant;
- visual pacing;
- semantic image matching.

Required question:

```text
Are we materially below the strongest competitor
in useful visual/media support?
```

If YES:

Phase 1 cannot receive full visual/media planning approval without:

- a recovery plan;
- an explicit Human waiver;
- or a justified product/genre reason.

## 5.8 Complete Media Lifecycle

For pages where media matters, planning must progress through:

```text
Media Need
→ Candidate
→ Rights / Human Risk Decision
→ Human Decision
→ Integration
→ Visual Gate
```

Conceptual states:

### Media Need

```text
HIGH PRIORITY
RECOMMENDED
OPTIONAL
NO MEDIA NEEDED
```

### Candidate

```text
NOT FOUND
FOUND
SEMANTICALLY VERIFIED
```

### Rights

```text
VERIFIED
UNRESOLVED
HUMAN RISK ACCEPTED
NOT REQUIRED FOR EMBED
```

### Integration

```text
NOT INTEGRATED
INTEGRATED
FALLBACK ONLY
```

### Visual Gate

```text
PENDING
PASS
REVISE
BLOCK
```

These states belong in:

- `MEDIA_DECISION_TABLE.md`;
- `CURRENT_STATUS.md`;
- or an existing reconciliation artifact.

They must NOT move into Runtime Page Inventory.

## 5.9 Re-define `NO MEDIA NEEDED`

V2.6 definition:

```text
NO MEDIA NEEDED
=
This page remains useful, comprehensible,
and visually complete without media.
```

It must NOT mean:

```text
rights uncertain
→ therefore no media needed
```

Rights status and media need are separate decisions.

## 5.10 Homepage Rule

If homepage media is classified:

```text
HIGH PRIORITY
```

but reaches Human Visual Gate with no resolved media integrated:

```text
REVISE
```

unless Human explicitly approves a no-media exception.

## 5.11 Media Readiness Audit

Add lightweight audit behavior.

Example:

```text
HIGH PRIORITY MEDIA UNRESOLVED
```

Suggested severity:

- homepage unresolved high-priority media → `BLOCK / HUMAN WAIVER REQUIRED`
- high-priority guide media unresolved → `REVISE / WARNING`
- recommended media unresolved → informational warning

No universal media quota.

## 5.12 Third-party Media Failure State

Afterworld proved that a technically present iframe can still look broken.

Require intentional visual fallback for third-party media that may fail, delay, or be blocked.

Minimum quality target:

- branded/dark fallback frame;
- video title/context;
- play/source affordance;
- source link;
- no large empty broken-looking rectangle.

Do not automatically add a new media abstraction or DSL.

## 5.13 Human Visual Gate

Phase 4 Human Visual Gate must independently approve:

```text
Technical Visual QA
Game Recognition
Visual Identity
Media Density
Semantic Media Matching
Responsive Visual
Media Failure State
```

Technical layout PASS is necessary but not sufficient.

## 5.14 Layer Ownership

### GAME_SOP

Strong ownership.

Define:

- Game Recognition Gate;
- official visual evidence requirements;
- competitor media benchmark;
- media lifecycle;
- `NO MEDIA NEEDED`;
- Human Visual approval criteria.

### GAME_CODEX_MASTER_PROMPT

Strong ownership.

Enforce:

- Phase 1 visual evidence;
- competitor media benchmark;
- late-stage high-priority media unresolved handling;
- Human Visual Gate output;
- third-party failure-state checks.

### GAME_SITE_STARTER

Light ownership for governance itself.

Starter should only add:

- lightweight media readiness validation;
- reusable failure-state behavior if proven to belong in Stable Core.

## 5.15 Acceptance Criteria

V2.6 must not allow full Human Visual PASS when:

- homepage lacks sufficient game recognition;
- high-priority media remains unresolved without Human waiver;
- strongest competitor materially outperforms useful media support;
- game palette is not recognizably reflected;
- media is semantically mismatched;
- third-party media produces a broken-looking blank state.

# 6. Package D — Starter Media Contract Fixes

## 6.1 Problems Covered

This package covers:

- V2.6-06 — Site Chrome Asset Misclassification
- lightweight media readiness validation required by Package C

## 6.2 Observed Logo Failure

Recent sites exposed a technical bug:

- logo file exists;
- header renders it using `<img>`;
- media audit assumes `<img>` means page content media;
- page-content audit rejects the logo because it is not part of the content media contract.

The workaround was to move the logo into a decorative CSS background while preserving brand text and accessible home-link naming.

That workaround should not become the permanent architecture.

## 6.3 Correct Asset Model

Starter must distinguish:

### Content Media

Examples:

- article hero
- inline screenshot
- gallery
- video poster
- map screenshot

### Site Chrome Assets

Examples:

- logo
- favicon
- header brand mark
- footer mark
- decorative UI assets

## 6.4 Validation Contract

Correct design:

```text
content media audit
→ validates content media only

chrome asset validation
→ validates allowed site chrome assets
```

Do not make Runtime Page Inventory own this distinction.

## 6.5 Accessibility Rule

If the logo is decorative and visible brand text already provides semantics:

- CSS background or `alt=""` is valid.

If the logo itself carries branding semantics:

- semantic `<img alt="...">` must remain allowed.

Do not force every logo into decorative-only CSS.

## 6.6 Required Starter Changes

Update only proven technical areas:

- media audit;
- header/logo contract;
- site chrome asset validation;
- relevant tests;
- lightweight high-priority-media unresolved audit.

## 6.7 YouTube Fallback Decision

Do NOT automatically promote the Afterworld YouTube fallback into Stable Core in the first V2.6 implementation.

Treat it as:

```text
proven project-edge pattern
```

until either:

- a third real-world game needs the same reusable behavior;
- or the Starter can adopt it without schema/API inflation.

If promoted, minimum reusable behavior should remain narrow:

- intentional fallback frame;
- title;
- source/play affordance;
- iframe overlays when ready.

No arbitrary iframe abstraction.

## 6.8 Layer Ownership

### GAME_SITE_STARTER

Strong ownership.

### GAME_CODEX_MASTER_PROMPT

Medium/light ownership:

- confirm logo is visible;
- confirm accessible naming;
- confirm media audit does not reject legitimate chrome assets.

### GAME_SOP

Light clarification only:

```text
site chrome assets are not page content media
```

## 6.9 Acceptance Criteria

- valid header logo does not fail page-content media audit;
- semantic `<img alt="...">` remains possible;
- decorative logo remains possible;
- high-priority unresolved media can be surfaced without turning Starter into a workflow engine;
- Runtime Page Inventory remains publication SSOT.
